# Port Between Repositories

## Summary

- **Purpose:** bring proven code or docs into a new repo without dragging along the source repo's
  coupling, and keep a traceable link back to the origin.
- **Five rules:**
  1. Cite the source at the top of every ported file: `Ported from <project>: <path>` (+ commit if known).
  2. Strip source-specific dependencies (DB layer, frameworks, domain regexes, document types, config
     names) unless the target genuinely needs them.
  3. Keep the core logic and its edge-case handling; do not "simplify" what the source learned the hard way.
  4. Add tests in the target repo, including the source repo's relevant tests adapted.
  5. Record what differs from the source and why.
- **Reference format:** always `<project>: <repo-relative path>` - never a local absolute path.
- **Output:** ported files, tests, a differences note (in the file docstring, the PR description or the
  plan), docs updated.
- **Config keys used:** `[gate].commands`, `[gate].lint`, `[project].max_file_lines`,
  `[project].doc_language`, `[docs_map]`; read with `"${CLAUDE_PLUGIN_ROOT}/scripts/dw" config --json` (see `${CLAUDE_PLUGIN_ROOT}/skills/dev-triage/references/config-defaults.md`).

## 1. Before copying

### 1.1 Understand the source

- Open the source files and their tests; read the source repo's rules for that area (its `AGENTS.md`,
  `.claude/rules/`) to learn which constraints are general and which are local.
- Note the source commit (`git -C <source repo> rev-parse --short HEAD`) for the citation.
- List every import and external call: classify each as **core** (needed for the logic), **replaceable**
  (target has an equivalent), or **source-only** (drop).

### 1.2 Check the target's rules

- Read the target repo's `AGENTS.md`/rules: naming, file-size cap (`[project].max_file_lines`), test
  layout, language of docs and UI strings, forbidden dependencies.
- Search the target for an existing equivalent; extending it beats a parallel copy.
- Lane: a single self-contained module is usually L1; porting a subsystem or anything that changes the
  target's contracts is L2 (`dev-workflow:spec-plan`).

## 2. Porting

### 2.1 Code

- Top-of-file docstring/header, adapted to the language's comment syntax:

  ```text
  Ported from <project>: <path/in/source/repo.py> (<commit>).
  Changes: <dropped X>, <replaced Y with Z>, <renamed ...>.
  ```

- Remove source-only coupling: database/session objects, orchestration frameworks, domain-specific
  regexes and enum values, logging/metrics helpers the target lacks. Replace with parameters or the
  target's equivalents.
- Keep names meaningful in the target domain; rename source-domain names that would mislead.
- Keep constants named and in one place; carry over comments that explain *why*.
- Respect the target's file-size cap: split by responsibility while porting rather than after.

### 2.2 Docs, rules and configuration

- Port the principle, not the incident: drop source project names, ticket numbers, migration numbers and
  file paths unless they are labelled as an example (`e.g. in <project>: <path>`).
- Parameterise anything project-specific (paths, commands, keys) through the target's config.
- Rewrite in the target's documentation language and structure (summary first, top-down).
- Never copy secrets, credentials, internal hostnames or customer data; replace with placeholders and
  point to the target's secret mechanism.

### 2.3 Tests

- Port the source tests that exercise the core logic; rewrite fixtures to be generated by code in the
  target (no copied customer files).
- Add a test for every behaviour you changed or dropped, so the difference is pinned.
- Tests must pass in the target's normal gate without the source repo present.

## 3. Verify and record

- Run the new tests, then `[gate].commands` and `[gate].lint`.
- `grep` the ported files for leftovers: source project name, source package/module names, absolute
  paths, source-only identifiers.
- Differences note (docstring "Changes:" line plus the PR description or plan):

  | Area | Source | Target | Reason |
  |---|---|---|---|
  | Dependency | | | |
  | Behaviour | | | |
  | Tests | | | |

- Update target docs per `[docs_map]`. If the port reveals a bug in the source, report it; do not fix
  the source repo unless asked.

## Brain/hand split

- **Brain:** decides scope (what to port, what to drop), checks the target for an existing equivalent,
  reviews the result for leftover coupling.
- **Hand:** reads the source (read-only), writes the ported files and tests, runs the gate. The brief
  names the source as `<project>: <path>`, the target location, and the dependencies to drop. Write
  scope is the target repo only; the source repo is read-only.
